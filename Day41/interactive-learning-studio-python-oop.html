Module 01

Foundations — Classes & Objects

Beginner

What is a class, really?

A class is a blueprint for creating objects. It doesn't do anything by itself — it just describes what data (attributes) and behavior (methods) every object built from it will have. An object (or instance) is one concrete thing made from that blueprint.

AnalogyThink of a class as a cookie cutter and objects as the cookies. The cutter defines the shape (attributes) and how you can decorate it (methods), but each cookie is separate dough — changing one cookie's icing doesn't change another's.
class Dog:
    # the blueprint
    def __init__(self, name, breed):
        self.name = name       # attribute
        self.breed = breed     # attribute

    def bark(self):        # method
        return f"{self.name} says Woof!"

rex = Dog("Rex", "Labrador")   # rex is an object/instance
print(rex.bark())                # Rex says Woof!

The role of __init__ and self

__init__ is the constructor — Python calls it automatically the moment you create an object, so you can set up its starting attributes. self is simply "the object currently being worked on"; every instance method receives it automatically as the first parameter so it knows which object's data to use.

Class attributes vs. instance attributes

Instance attributeClass attribute
Set in __init__ via self.x = ...Defined directly in the class body

Common misconceptionBeginners often think self is a keyword. It's not — it's just a convention. You could name it anything, but every experienced Python developer expects self, so deviating breaks readability for no benefit.

Module 02

Building Relationships — Inheritance

Beginner → Intermediate

Inheritance: reusing and specializing behavior

Inheritance lets one class (the child or subclass) reuse and extend the attributes and methods of another (the parent or superclass). It models an "is-a" relationship: a Dog is an Animal.

class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound."

class Dog(Animal):              # Dog inherits from Animal
    def speak(self):        # overriding the parent method
        return f"{self.name} says Woof!"

class Puppy(Dog):
    def speak(self):
        parent_line = super().speak()   # call the parent's version too
        return parent_line + " (but it's more of a yip)"
AnalogyInheritance is like a family recipe passed down through generations. A grandchild's recipe starts from grandma's base recipe (the parent class) but can tweak an ingredient (override a method) or add a new step (add a new method) — while still keeping most of the original intact.

Method Resolution Order (MRO)

When you call a method, Python looks for it starting at the object's own class, then walks up the chain of parents until it finds a match. super() lets a child explicitly call the parent's version instead of fully replacing it.

Without inheritanceWith inheritance
Copy-paste speak, eat, sleep into every animal classDefine once in Animal, reuse in every subclass
Bug fixes must be repeated everywhereFix once in the parent, all children benefit
No shared "type" relationshipisinstance(rex, Animal) is True
Common misconceptionOverriding a method does not delete the parent's version — it just means Python finds the child's version first. The parent version still exists and can be reached with super().

  • Inheritance models "is-a" relationships and lets subclasses reuse parent code.
  • Overriding replaces a method's behavior in the subclass; super() lets you still call the parent's version.
  • Python resolves method calls by walking the class hierarchy (MRO).
  • Deep, tangled hierarchies can become hard to follow — inherit only when there's a genuine "is-a" relationship.

Module 03

Practical Application — Encapsulation & Polymorphism

Intermediate

Encapsulation: protecting internal state

Encapsulation means bundling data and the methods that operate on it together, and controlling how that data is accessed or changed from outside. Python signals "private" intent with a leading underscore (convention, not enforced) or a double underscore (name-mangled, harder to access accidentally).

class BankAccount:
    def __init__(self, balance):
        self.__balance = balance      # "private" attribute

    def deposit(self, amount):
        if amount > 0:
            self.__balance += amount

    @property
    def balance(self):          # controlled, read-only access
        return self.__balance

acc = BankAccount(100)
acc.deposit(50)
print(acc.balance)   # 150 — but acc.__balance directly is blocked
AnalogyEncapsulation is like a vending machine. You interact through buttons (public methods) — you never reach in and rearrange the snacks yourself (internal attributes). The machine controls exactly how its internal state can change.

Polymorphism: one interface, many behaviors

Polymorphism means different classes can be used interchangeably if they share a common interface — the same method name behaves appropriately for each type.

for creature in [Dog("Rex"), Cat("Tom"), Animal("???")]:
    print(creature.speak())   # each object responds in its own way

# Rex says Woof!
# Tom says Meow!
# ??? makes a sound.
Duck typing (Python style)Formal interfaces (other languages)
"If it has .speak(), treat it like something that speaks"Must explicitly declare it implements an interface
Flexible, but errors surface at runtimeStricter, errors caught earlier by the compiler
Common misconceptionPolymorphism is not only about inheritance. In Python, any two unrelated objects that both implement .speak() can be used polymorphically — this is called duck typing: "if it walks like a duck and quacks like a duck…".

  • Encapsulation controls access to internal state via methods/properties instead of direct attribute access.
  • @property lets you expose a method as if it were a plain attribute.
  • Polymorphism lets different classes respond to the same method call in their own way.
  • Python favors duck typing over strict interface declarations.

Mastery — Dunder Methods, Composition & Design

Advanced

Dunder methods: hooking into Python's own syntax

"Dunder" (double-underscore) methods let your objects integrate with built-in syntax: printing, comparison, length, arithmetic, and more. You've already met __init__ — here are more.

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"

    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)

    def __eq__(self, other):
        return self.x == other.x and self.y == other.y

v1, v2 = Vector(1,2), Vector(3,4)
print(v1 + v2)     # Vector(4, 6)  — __add__ is called
print(v1 == v2)    # False          — __eq__ is called

Composition vs. inheritance

Composition builds objects out of other objects ("has-a") rather than extending a class ("is-a"). It's often more flexible than deep inheritance chains.

class Engine:
    def start(self):
        return "Engine roaring"

class Car:                        # Car HAS-A Engine (composition)
    def __init__(self):
        self.engine = Engine()

    def start(self):
        return self.engine.start()
AnalogyInheritance is like being born into a family — you inherit traits you can't easily swap out. Composition is like hiring a specialist contractor: your Car doesn't need to be an Engine, it just needs to have one — and you can swap in a different engine without redesigning the car.

Abstract base classes: enforcing a contract

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...    # subclasses MUST implement this

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2

# Shape() -> TypeError: Can't instantiate abstract class
Common misconception"Favor composition over inheritance" doesn't mean inheritance is bad — it means don't reach for inheritance by default. Use inheritance for genuine "is-a" relationships with shared behavior; use composition when you just need to reuse a capability.

Key takeaways

  • Dunder methods let your objects hook into Python's built-in syntax (printing, operators, length, iteration).
  • Composition ("has-a") is often more flexible than deep inheritance ("is-a").
  • Abstract base classes enforce that subclasses implement required methods.
  • Good OOP design favors clarity and the right tool for the relationship, not maximal inheritance.
